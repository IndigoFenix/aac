I'd like us to go over the logic with the live-relay chat system. There are some issues with how    
  it's picking up and recording data.
  Here's how it should be working:                                                                          - When a session is initialized, a message is sent to the monitor agent. The monitor agent reads    
  the student notes and any other information it needs. It creates a system-level prompt, which             includes both the user-defined prompt (defined in the student object from the database) as well as  
  any additions the monitor wants to add.
  - This prompt, created by the monitor, is added to the session log and session state (in history)   
  and saved to the database immediately.
  - The interactive agent then opens a channel (we are using Gemini).
  - Every time the interactive agent opens a channel (including later when the channel renews) it     
  must load the history (NOT the log) from the session state in the database, strip all actions from  
  the monitor agent EXCEPT messages it created for the interactive agent, and then append all
  pending_messages to that history (do not save this to the database). The history + pending_messages 
   forms the context the AI uses.                                                                         
  - Gemini should have a persistent channel open.                                                         
  - Whenever Gemini hears or observes anything, it should create a message. This message is added to      
  pending_messages in the database for that session *immediately* (unless we are about to move them -     
   see below), in addition to being stored in the local context, which Gemini should have in context      
  at all times. It should not be added to the state history or log yet.                                   
  - The monitor agent should be called periodically, or when the interactive agent calls it. The          
  monitor agent should NEVER start up again while it is already running. If the monitor would be          
  called and it is already running, set a flag to call it again after it is done running.                 
  - Whenever the monitor agent is about to start up, the FIRST thing we do is load the chat state,        
  log, and pending_messages. pending_messages are added to the chat state history and log. All three      
  columns are then updated atomically.                                                                    
   - While this is happening (before loading the database data until after saving it) any messages        
  generated by Gemini should NOT be added to pending_messages. They should be stored in memory until      
  the atomic action is complete, so they don't get lost when we wipe the pending_messages in the          
  database.                                                                                               
  - If pending_messages is empty, the monitor has nothing to do, so skip it.                              
  - The monitor agent does its thing using the context from chat state, which now includes                
  pending_messages. It may run all tools it needs, which may include truncating data.                     
  - When the monitor agent is done, the chat state and log are updated in the database. (Chat state       
  history may be truncated and summarized by the monitor; it is used by both agents for context. The      
  log is never truncated and is stored for our records.) After this, the monitor agent is unlocked        
  and can be started up again when needed.                                                                
  - If the monitor produced an instruction message, it should be added to the local context so Gemini     
   can see it. We do not need to update the local context other than this; any summarization should       
  handle the next time the channel is re-opened.                                                          
  - When the channel closes, trigger the monitor one last time (if it is already running, flag it to      
  run again when done unless pending_messages is empty.) Tell it that the session was closed and          
  instruct it to perform a summary.                                                                       
                                                                                                          
  This should ensure that data never gets lost. Go over it and look for flaws in the plan, and if it      
  looks good, implement it.
